> 아래는 **직접 제공한 버그/문제 목록**과, 요청하신 대로 이전 대화·수정 이력을 맞춰 정리한 것이다. 코드만 보고 유추한 항목은 넣지 않았다.  
> 심각도: `[심각: 데이터 손실/보안]` · `[경미: 운영 불편]`

## 1. 배정 알고리즘 — 빈자리 있는데 배정 안 됨 · `[심각: 데이터 손실/보안]`

**문제**  
여러 알고리즘을 거쳐 고쳐도, 빈 슬롯이 있는데 대기자만 남는 문제가 반복됐다. (스피드업 높은 사람부터 배정, 배정 후 자리 없으면 다른 선호로 옮기기 등 시도.)

이전 대화·커밋에서 확인되는 경과:

1. **제출 즉시 배정** — 블록에 Available이 남아 있는데 waitlist에 사람이 있는 사례 발생 (예: SU 340d 대기자 vs 같은 블록 빈 슬롯).
2. **마감 후 일괄 배정**으로 전환.
3. **Hopcroft-Karp** (블록별 Top-N 자격 + 최대 매칭).
4. 그래도 빈자리 남음 → **2-phase** (1차 Top-N 매칭 후, 빈 슬롯 블록만 제한 완화해 2차 매칭).
5. 최종적으로 문서·README에 잡힌 결함 유형은 V1(빈 슬롯+대기자), V4(스피드업 역전) 등.  
   → **V1~V5 정의·합격 기준은 [2. 설계 및 구현 계획](./2-설계-및-구현-계획.md#설계-요구사항-verifyassignment-v1v5) 참조.**

**원인**  
구버전 Hopcroft-Karp(및 2-phase 보완) 구조로는 V1·V4를 안정적으로 없애기 어려웠음. (제공 정리·설계 페이지 MCMF 기술 근거·`docs/RESERVATION_SYSTEM.md` §8·§18.)

**해결**  
**MCMF(Min-Cost Max-Flow)** 로 교체. 스피드업 순위를 비용으로 넣고, Top-N 미달은 큰 페널티 비용으로 단일 pass에서 처리.

**현재 상태 (로컬 실측)**  
`npm run verify:assignment`를 로컬에서 실행한 결과 (현재 `.env.local`이 가리키는 DB·`current_cycle_id` 기준):

```
요약: 에러 0건 / 경고 0건
```

즉 **지금 이 사이클에서는 V1~V5 위반 0건**이다. (과거 목표 서술과 별개로, 위가 실측 상태.)

**배운 점**  
휴리스틱/2-phase로 빈자리를 “메우는” 방식은 우선순위 역전을 같이 만들기 쉽다. 검증 기준(설계 페이지)을 먼저 두고 알고리즘을 바꾸는 편이 나았다.

## 2. 트랜잭션 안전성 · `[심각: 데이터 손실/보안]`

**문제**  
신청 처리 로직이 원자적이지 않아 롤백 문제가 있었음.

**원인**  
앱 단에서 players / preferences / reservations를 여러 번 나눠 호출.

**해결**  
`submit_multi_day_reservation` RPC(v8)로 이관. Postgres 단일 함수 호출로 원자성 확보.  
(내부 `BEGIN`/`EXCEPTION` 블록은 원자성과 무관 — 에러 메시지 포맷용.)

**미해결 — raw Postgres 에러 노출 (로컬 재현)**  

`(elem::TEXT)::INTEGER` 캐스트는 INSERT의 `EXCEPTION` 블록 **밖**에 있어, 실패 시 `RAISE EXCEPTION 'Failed to …'`로 감싸지지 않고 PostgREST/Supabase 클라이언트로 그대로 올라간다. `lib/assignment.ts`의 `rpcErrorMessage()`는 메시지에 `"Failed to "`가 있을 때만 잘라 내고, 아래처럼 없으면 **전문을 그대로** 반환한다.

로컬에서 service role로 RPC를 잘못된 `preferred_blocks`와 함께 호출해 캡처한 결과:

| 입력 (`preferred_blocks`) | `error.message` (호출자 노출) | code |
|---------------------------|-------------------------------|------|
| `["not-an-int"]` | `invalid input syntax for type integer: ""not-an-int""` | `22P02` |
| `[{ "x": 1 }]` | `invalid input syntax for type integer: "{"x": 1}"` | `22P02` |
| `[null]` | `invalid input syntax for type integer: "null"` | `22P02` |
| `[""]` | `invalid input syntax for type integer: """"` | `22P02` |

**노출되는 것:** Postgres SQLSTATE(`22P02`), 타입명 `integer`, **거부된 입력값 원문**.  
**이 재현에서 안 보인 것:** 테이블명(`preferences` 등), 컬럼명, 스키마/함수 본문 전체.  
`details` / `hint` 필드는 `null`이었다.

정상 앱 경로(시크릿 URL·구글 폼)는 TS에서 숫자를 넣지만, RPC를 직접 치거나 웹훅이 깨진 payload를 넘기면 위 메시지가 API/클라이언트에 그대로 나갈 수 있다.

**배운 점**  
다중 테이블 쓰기는 RPC 한 방으로 묶는 편이 안전하다. 다만 캐스트·검증 실패는 앱/RPC에서 메시지 포맷을 고정해야 한다.

## 3. 감사 로그 부재 → 사후 추가 · `[경미: 운영 불편]`

**문제**  
삭제/취소/재제출 액션이 기록되지 않음.

**원인**  
초기 설계에 audit trail이 없었음.

**해결**  
`audit_log` 테이블(v9, v10) — `delete_preference`, `cancel_reservation`, `resubmit_preference`.

**배운 점**  
운영 중 “누가 무엇을 지웠는지”가 필요해지면 뒤늦게라도 스냅샷 로그를 넣는 수밖에 없다.

## 4. 숨은 파괴적 사이드이펙트 (`checkReservation`) · `[심각: 데이터 손실/보안]`

**문제**  
조회 전용으로 보이는 `checkReservation`이 조회 중 `players` 행을 삭제함.

**원인**  
preferences가 없을 때 orphan 정리 겸 players DELETE를 넣어둠 (의도적 정리로 보였으나 조회 API에 두면 위험).

**발견 경위**  
커밋·이슈 트래커에 “유저 신고/모니터링 알람” 기록은 없다.  
이전 대화([실사용 판단·checkReservation 점검](aa289664-ccb7-44ee-8dc5-dde71cb8bd76))에서 **코드를 직접 물어보며 조회 경로의 DELETE를 확인**한 뒤 제거를 지시함 → **코드 리뷰/본인 점검**에 가깝다.

**수정 커밋**  
`4f14f1a` (2026-07-06) *Migrate reservation submission to RPC function*  
본문: *Also remove a bug that was deleting players when no preferences existed in checkReservation.*

**실제 영향 범위**  
커밋 메시지·관련 이슈에 **삭제된 행 수·복구 여부**는 없음.  
조건상: `/r/[token]/check`에서 Player ID 조회 시 해당 cycle에 preferences가 없으면 `players` 행 DELETE.  
`[본인 확인 필요: 실제 삭제된 players 행 수, 복구 여부]`

**해결**  
해당 DELETE 제거. 현재 정리 책임은 `archive_and_reset_cycle`이 전담.

**배운 점**  
GET/조회 경로에 DELETE를 두지 말 것. 정리는 reset 같은 명시적 운영 액션에만.

## 5. 배정 후 잠금 미적용 (미해결) · `[심각: 데이터 손실/보안]`

사실(상수만 있고 미강제)은 [2. 설계 — 미구현/잔여 갭](./2-설계-및-구현-계획.md#미구현--잔여-갭-사실만)에만 적어 두고, 여기서는 **언제 터지는지**만 적는다.

**타임라인 (진행 로그와 동일 사건)**  
[4. 진행 로그 · 2026-W25](./4-진행-로그.md) — 대화상 배정 후 `ASSIGNMENT_LOCKED`로 구글 폼이 **409** 거절된 적이 있음. 같은 주 커밋 `e96d384`(2026-06-16) 본문에는 *reject … after assignment run*이 있었음. **이후 정책이 바뀌어 현재는 제출 경로에서 미강제.**

**왜 아직 안 고쳤는지**  
코드/커밋에 “의도적 보류” 기록은 없음. SOP로 배정 후 시크릿 URL을 닫아 두어 **증상이 잘 안 드러나는 상태**로 운영 중.

**위험 시나리오**

1. 배정 후 Admin이 **Open secret URL**을 연 채 두면, 연맹원이 `/r/...`로 재제출 → 해당 player의 **assigned/eliminated reservations 삭제** + preferences 교체. `/status`·본인 조회에서 슬롯이 사라짐.
2. **구글 폼**은 `reservation_open`과 무관(`skipOpenCheck`). 배정 후에도 폼이 열려 있으면 같은 삭제가 발생. 실수로 재제출한 사람이 자기 자리를 지울 수 있음.
3. `ASSIGNMENT_LOCKED_MESSAGE`만 보고 “막혀 있다”고 착각하면 운영 사고.

## 6. 구글 폼 vs 시크릿 URL — 마감 통제 비대칭 · `[심각: 데이터 손실/보안]` · **미해결 (SOP로 우회)**

**문제**  
시크릿 URL은 `reservation_open`으로 서버가 닫을 수 있지만, 구글 폼은 **Forms에서 “응답 수락 중지”**를 따로 해야 막힘. 한쪽만 닫으면 마감 후에도 신청이 들어올 수 있음.

**원인**  
두 채널의 게이트가 애초에 다름 (`skipOpenCheck` 등).

**미해결 (SOP로 우회)**  
코드로 한 방에 묶인 해결은 없음. 운영 문서로 2단계 마감을 명시 (`f00f1be` 등).  
대시보드 Close secret URL만 하고 구글 폼을 깜빡하면, **마감 이후·배정 직전/직후**에도 preferences가 계속 쌓이거나(배정 전이면 다음 Run에 포함, 배정 후면 기존 슬롯 삭제 재제출 가능) 공정성·데이터가 깨질 수 있음.

**배운 점**  
채널이 둘이면 마감도 둘. SOP에 “동시에 닫기”를 박아 둬야 함.

## 7. 검증 부재 — `day_of_week` CHECK (미해결) · `[심각: 데이터 손실/보안]`

스키마에 CHECK가 없다는 사실은 [2. 설계 — 미구현/잔여 갭](./2-설계-및-구현-계획.md#미구현--잔여-갭-사실만) 참고. 여기서는 위험만.

**왜 아직 안 고쳤는지**  
커밋·문서에 보류 사유 없음. 앱·정상 RPC 경로는 `'mon'|'tue'|'thu'`만 넣는다는 전제에 기대는 중.

**위험 시나리오**

1. RPC/`preferred_blocks`와 달리 `day_of_week`에 잘못된 문자열(예: `monday`, `fri`)이 직접 insert되면 **조용히 성공**.
2. 배정·verify·Admin 그리드는 `mon/tue/thu`만 순회 → 그 행은 **배정 대상에서 빠지거나**, 집계/Export에서 **누락된 것처럼** 보임.
3. 원인 추적이 “신청 안 한 사람”으로 오인되기 쉬움 (에러가 안 남음).

## 8. 로컬–배포 코드 드리프트 (진행 예정) · `[경미: 운영 불편]`

**문제**  
`scripts/appscript/onFormSubmit.gs` 로컬 파일이 배포된 Apps Script와 어긋남 (이메일 컬럼 인덱스). 문서도 `row[1]`=Player ID로 되어 있던 것과 실제 `row[2]`가 불일치했던 이력이 있음.

**현황**  
로컬 파일은 현재 이메일 ON 기준 `row[2]`=Player ID로 맞춰져 있음. 로컬·README·`RESERVATION_SYSTEM.md`·**실제 배포 스크립트** 전부 재동기화는 **진행 예정**.
